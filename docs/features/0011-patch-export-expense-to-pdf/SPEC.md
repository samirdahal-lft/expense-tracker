**Severity:** minor
**Source:** feature request — users want a portable, printable record of their expenses

**Current behavior:** There is no way to download or export the expense list; users can only
view expenses in the browser. No export mechanism of any kind exists in the app.

**Expected behavior:** A user can click an "Export PDF" button on the expense list page and
receive a PDF file download containing their currently-filtered expense list (date, category,
amount in NPR, and note columns) along with a summary row showing the total. The PDF is
generated by the backend and streamed to the browser.

**Must NOT change:** Existing expense listing, filtering, creation, editing, and deletion
endpoints and their behavior remain unchanged. Money continues to be represented as integer
whole NPR throughout. The repository → service → router layering is preserved.

## TSD S-0011.01 — Backend PDF export endpoint + frontend download trigger

> Behavior + contracts ONLY — never the library/method/pattern. The Critic anchors to THIS
> section (snapshot frozen at `lane start`), exactly as it would to a TSD.md section.

| Aspect | Spec |
|--------|------|
| Interfaces | **Backend:** `GET /api/expenses/export/pdf` — accepts the same optional query params as the expense list endpoint (`start_date`, `end_date`, `category_id`); returns `Content-Type: application/pdf` with `Content-Disposition: attachment; filename="expenses.pdf"`. **Frontend:** an "Export PDF" button rendered in the expense list toolbar; clicking it triggers a fetch to the export endpoint and initiates a browser file download. |
| Data / State | The endpoint reads from the existing expenses + categories tables via the repository layer. No new persistent state is written. Amounts are integer whole NPR throughout; the PDF renders them as plain integers (e.g. "1500"). |
| Behavior | 1. The backend receives the export request (with any filters), queries all matching expenses through the service → repository chain, and generates a PDF table with columns: Date, Category, Amount (NPR), Note. A totals row appears at the bottom showing the sum of amounts. 2. The PDF is returned as a binary stream with the correct content-type and disposition headers so the browser downloads it automatically. 3. If no expenses match the filters, the PDF still renders with only the header row and a "No expenses" message (not an error). |
| Boundaries | SQLite (accessed only via the repository layer). The PDF-generation Python library is an internal implementation detail — tests fake/assert the output bytes, not the library calls. |
| Tests | **Backend (pytest):** (a) unit test on the service: given a list of expense rows, the returned PDF bytes start with `%PDF` and the content-type is correct; (b) integration test on `GET /api/expenses/export/pdf` via FastAPI TestClient: returns 200, `application/pdf` content-type, non-empty body; (c) integration test with an active date filter: only expenses in the range appear (verified by checking the PDF byte length changes or by parsing the returned bytes). **Frontend (Vitest):** a smoke test that the "Export PDF" button renders in the expense list component and that clicking it calls the API export function. |

## Task T-export-expense-to-pdf-72zrha — Backend PDF endpoint + frontend download button

**Slice:** complete vertical — new backend endpoint + frontend button that calls it, end-to-end, with tests at both layers

**Acceptance criteria:**
- [ ] AC-1 [behavior]: `GET /api/expenses/export/pdf` returns HTTP 200 with `Content-Type: application/pdf` and a non-empty body containing valid PDF bytes (`%PDF` magic bytes present).

## Execution Plan

> Approved BY the spec stamp: `lane start` copies this section verbatim into the worktree's
> exec-plan.md and carries your stamp onto it — no separate plan gate. Keep it last in this file.

**Approach:** Add a new `GET /api/expenses/export/pdf` FastAPI route that flows through the existing `router → service → repository` chain. The service queries matching expenses (reusing or calling the existing expenses repository filter), assembles the data, and hands it to a PDF-generation helper (using `fpdf2` — a pure-Python library with no system dependencies). The route returns a `StreamingResponse` with the correct headers. On the frontend, add an `exportPdf` function to the typed API client module (`src/api/`) and a button in the expense list toolbar that calls it and triggers a browser download via a Blob URL.

**Boundaries & mocks:** SQLite is real in integration tests (FastAPI TestClient with an in-memory or temp-file DB seeded with fixture rows). The PDF library is NOT mocked — tests assert on the returned bytes. Frontend tests mock the API client module to verify the button wires up correctly.

**Behaviors (TDD order):**
- B-1: Backend — `GET /api/expenses/export/pdf` returns 200 + valid PDF bytes for a seeded dataset (failing test first via TestClient; then implement the route + service method + PDF helper).
- B-2: Backend — filtered export: passing `start_date`/`end_date` limits rows in the PDF (failing test asserts on response body or fixture record count; then wire filters through the service call).
- B-3: Frontend — "Export PDF" button renders and calls the API client export function on click (failing Vitest test first; then add `exportPdf` to the API client and the button to the toolbar component).

**Open questions:** none
